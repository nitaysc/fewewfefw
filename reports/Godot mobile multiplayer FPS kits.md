# Build your phone FPS from parts

**Short answer: nobody makes a Godot version of Cowsins' FPS Engine, and no Godot 4 kit, free or paid, comes with everything at once (lots of weapons, ADS, recoil, fancy movement, enemies, menus, online play and phone touch controls).** You can still get close by putting a few free pieces together. All of them use the MIT license, so they're fine in your public GitHub repo. The closest free all-in-one kit is **bukkbeek's GodotFPS-Template** (MIT, Godot 4.6, ADS, 5 working weapons, zombie AI, HUD, pickups) ([README](https://raw.githubusercontent.com/bukkbeek/GodotFPS-Template/HEAD/README.md)). The best ready-made online FPS base is **TheDahoom's FPS-Multiplayer-Template** (MIT, menus, join by IP) ([GitHub](https://github.com/TheDahoom/FPS-Multiplayer-Template)). **No kit has touch controls built in**, so those come from the free **Virtual Joystick** addon plus a small "drag to look" script ([GitHub](https://github.com/MarcoFazioRandom/Virtual-Joystick-Godot)). The biggest catch for playing with friends on phones is that **mobile data usually blocks one phone from hosting a game the others join** (this is called CGNAT), so you need either a relay service or a small always-on server ([Godot Q&A](https://ask.godotengine.org/120755/my-game-is-working-on-lan-but-need-to-step-it-a-bit)). The good news: **building Android APKs entirely in GitHub Actions works fine with no computer**, because Godot is free and needs no license activation, unlike Unity ([Godot command line docs](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)).

## My recommendation

Here's the combo I'd go with for you. You only have a phone, your repo is public, and an AI edits files and builds through GitHub Actions.

**1. Engine: Godot 4.7.x (4.7.2 is the newest stable build the CI image has) using the Compatibility renderer.** The CI Docker image `barichello/godot-ci` has tags up to 4.7.2 ([Docker Hub](https://hub.docker.com/v2/repositories/barichello/godot-ci/tags?page_size=15&ordering=last_updated)). Godot's own docs say Compatibility gives "the best performance on all devices if you don't need advanced features", which matters if your friends' phones aren't all new ([Renderers docs](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)). A recent version also covers Google's 16 KB memory page rule, which needs Godot 4.5+ ([Godot forum](https://forum.godotengine.org/t/godot-and-google-play-policy-warning-about-16-kb-memory-page-size/120934)).

**2. Gameplay base: [bukkbeek/GodotFPS-Template](https://github.com/bukkbeek/GodotFPS-Template).** It's free on GitHub under MIT. It has ADS, a knife, pistol, assault rifle, burst rifle and LMG, ammo and reload, zombie enemies, a HUD and pickups ([README](https://raw.githubusercontent.com/bukkbeek/GodotFPS-Template/HEAD/README.md)). The itch.io page shows a $4.99 button, but the code on GitHub is free ([itch.io](https://bukkbeek.itch.io/godot-fps-template)). Fair warning: the author calls it a work in progress, and it was last updated in March 2026. If the AI finds it too messy, a cleaner plan B is the **Jeheno pair**: the [Advanced State Machine First Person Controller](https://github.com/Jeh3no/Godot-Advanced-State-Machine-First-Person-Controller) (MIT, updated 2026-11-02) plus the [Simple FPS Weapon System](https://github.com/Jeh3no/Godot-Simple-FPS-Weapon-System-Asset) (MIT, recoil, reload, ammo, weapon switching, tested on Godot 4.4 to 4.7) ([Asset Library](https://godotengine.org/asset-library/asset/4105)).

**3. Multiplayer: Godot's built-in multiplayer (ENet with MultiplayerSpawner and MultiplayerSynchronizer).** Use [TheDahoom's FPS-Multiplayer-Template](https://github.com/TheDahoom/FPS-Multiplayer-Template) as the example to copy for lobby, menus and syncing players. Keep it small, with 2 to 8 players.

**4. Connecting over the internet, in two steps.** *Step one (free, no accounts):* use the [netfox.noray](https://github.com/foxssake/netfox) addon with the free public noray server at `tomfol.io:8890`. It tries to connect phones directly and relays traffic when that fails. It's meant for testing only and has no uptime promise ([netfox](https://github.com/foxssake/netfox)). *Step two (reliable):* if you and your friends play a lot, rent a small server and have GitHub Actions deploy a "headless" (no-screen) copy of the game to it. **Hetzner starts at €5.99/month** ([Hetzner](https://www.hetzner.com/cloud/)). **Oracle has a free tier**, but it can shut down servers that sit idle for 7 days ([Oracle docs](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)).

**5. Touch controls: [Virtual Joystick](https://github.com/MarcoFazioRandom/Virtual-Joystick-Godot)** (MIT, about 990 stars) on the left side of the screen for moving. The right half of the screen is a drag-to-look area. Fire, ADS, jump, reload and crouch use Godot's built-in `TouchScreenButton`.

**6. Builds: GitHub Actions using the [barichello/godot-ci](https://github.com/abarichello/godot-ci) image.** Each push builds an APK and attaches it to a GitHub Release, which you download on your phone. Create your own signing key once and store it as a **GitHub secret, never as a file in the repo**, because the repo is public.

**What to skip:** the paid retro kits (their licenses forbid sharing the source, and your repo is public), GodotSteam (phones don't have a Steam client), Photon Fusion for Godot (still a preview), and Nakama's hosted cloud (costs hundreds of dollars a month). Details are below.

## No Godot kit matches FPS Engine, but free ones get closest

I found **no Godot product by Cowsins and no Godot port of FPS Engine**. There's an unrelated "Godot FPS Engine" by Finn on itch.io. It's a basic controller, and its page is now password-protected ([itch.io](https://finnder.itch.io/godot-fps-engine)). Every kit is missing at least part of the FPS Engine package. **None of the kits I found lists wallrun, dash or grapple as a feature**, so the AI would have to write those itself. Only two have **slide**: COGITO ([Asset Library](https://godotengine.org/asset-library/asset/2536)) and AxelReviron's early-stage template, which so far is mostly just movement ([README](https://raw.githubusercontent.com/AxelReviron/Godot-FPS-Template/HEAD/README.md)).

**A note on bukkbeek and multiplayer:** my research notes disagree on this one. One search snippet said its README describes **LAN multiplayer for up to 8 players** over ENet, with a headless `--host` option ([itch.io](https://bukkbeek.itch.io/godot-fps-template)). ## Online play from phones needs a relay or a server

Godot ships with working online play (ENet plus MultiplayerSpawner and MultiplayerSynchronizer). The official demos cover a bomber game, pong and WebRTC, but there's **no FPS demo** ([godot-demo-projects](https://github.com/godotengine/godot-demo-projects/tree/master/networking)). **Liblast**, the best-known open Godot FPS, now says in its own README that it is "NOT in a working state" ([Codeberg](https://codeberg.org/Liblast/Liblast)). The small MIT bases that do work, like TheDahoom's template and [djeanql/SimpleFPS](https://github.com/djeanql/SimpleFPS), connect by typing in an IP address and opening ports with UPnP. That works at home on Wi-Fi. **On mobile data it usually fails**, because most carriers use CGNAT: the phone gets a private address that nobody outside can reach, and port forwarding doesn't help ([Nextcloud forum](https://help.nextcloud.com/t/port-forwarding-not-working-with-android-phone-as-wifi-adapter/126516); [BATC forum](https://forum.batc.org.uk/viewtopic.php?p=31241)). Some carriers don't do this, so results vary ([BATC forum](https://forum.batc.org.uk/viewtopic.php?p=31233)).

There are two ways around it. The first is **a relay**: [noray](https://github.com/foxssake/noray) (MIT) tries a direct connection first, then passes traffic through itself if that fails. It plugs into Godot through the netfox addon, which also adds lag compensation. The catch is that netfox's examples were written for Godot 4.1 and its only sample game is a brawler, not an FPS, so the AI has less to copy from ([netfox](https://github.com/foxssake/netfox)). The second is **a dedicated server**: a cheap computer in the cloud with a public address. Every phone makes an outgoing connection to it, and CGNAT allows outgoing connections ([BATC forum](https://forum.batc.org.uk/viewtopic.php?p=31241)). The same Godot project gets exported a second time as a no-screen Linux server and started with a `--server` flag, a pattern shown in [rivet-gg/godot-docker](https://github.com/rivet-gg/godot-docker).

## Touch controls take one addon plus a small look script

I found **no Godot 4 "mobile FPS controls" kit**, and no open-source Godot 4 mobile FPS template with both a joystick and touch-look. The nearest is a third-person touch controller ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Femagood%2Fthird-person-godot-4)). The standard piece is [MarcoFazioRandom's Virtual Joystick](https://github.com/MarcoFazioRandom/Virtual-Joystick-Godot): MIT, Godot 4.2+, with fixed, floating and following modes. It can press your normal move actions, so the existing FPS code barely changes. Its FAQ gives two tips. Turn **"Emulate Touch from Mouse" ON and "Emulate Mouse from Touch" OFF**, and use `TouchScreenButton` for buttons so several fingers work at once. Looking around is a few dozen lines of GDScript. The script reads `InputEventScreenDrag` on the right half of the screen and keeps track of which finger is which, so moving and looking don't fight each other ([community guide](https://claudeskills.info/skills/thedivergentai/gd-agentic-skills/godot-adapt-desktop-to-mobile/)). For swipes and pinches there's [Godot Touch Input Manager](https://github.com/Federico-Ciuffardi/GodotTouchInputManager) (MIT). Paid joystick kits exist, like [Tripex-Studio's Multitouch Controls Kit](https://tripex-studio.itch.io/godot-mobile-multitouch-controls) at $6.99+, but the free ones cover what you need.

For phones, Godot's performance guide recommends **baked lighting, occluders, mesh LOD, MultiMesh and very little transparency** ([Optimizing 3D](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)). That's worth asking the AI to keep in mind when it builds maps.

## GitHub Actions can build your APK without a PC

This part is well covered. The command is `godot --headless --export-debug "Android" build/game.apk`. The preset name has to match `export_presets.cfg` (which must be committed to the repo), the output folder has to exist, and **mistyped options are silently ignored**, so a typo can fail without an error message ([command line docs](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)). The easiest route is running the job inside the [barichello/godot-ci](https://github.com/abarichello/godot-ci) Docker image (MIT, about 1.2k stars). It already has Java 17, the Android SDK and a debug signing key ([Dockerfile](https://raw.githubusercontent.com/abarichello/godot-ci/master/Dockerfile)). Its Android example lives in the GitLab file, not the GitHub one, but it copies over to GitHub Actions directly ([.gitlab-ci.yml](https://raw.githubusercontent.com/abarichello/godot-ci/master/.gitlab-ci.yml)). One wrinkle: the image's Android SDK (API 33, NDK r25) is older than what Godot 4.7's docs list (API 35, NDK r28b) ([Exporting for Android](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)). A plain APK should be fine. A Google Play AAB would need extra SDK installs. Other routes are [chickensoft-games/setup-godot](https://github.com/chickensoft-games/setup-godot) (set `use-dotnet: false` for GDScript) and [firebelley/godot-export](https://github.com/firebelley/godot-export).

**Signing matters most for you.** Android only installs an update over the old app if both were signed with the same key. So generate one keystore once, base64-encode it into a GitHub secret, and pass it in with the `GODOT_ANDROID_KEYSTORE_*` environment variables ([Exporting for Android](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html); [godot-ci README](https://github.com/abarichello/godot-ci)). Since your repo is public, **the keystore file must never be committed**. One known bug: if only some of the debug keystore variables are set, a release export fails with "debug settings must be all configured or none" ([issue #109551](https://github.com/godotengine/godot/issues/109551)). The same workflow can also export the Linux server build and copy it to your VPS over SSH, using a key saved as another secret. Tests can run headless with [gdUnit4-action](https://github.com/godot-gdunit-labs/gdUnit4-action), which gives the AI a way to catch broken code before you install anything. Building in the cloud also avoids Godot's Android editor, which the Virtual Joystick FAQ calls unstable ([GitHub](https://github.com/MarcoFazioRandom/Virtual-Joystick-Godot)).

## Conclusion

Godot has no ready-made equivalent of FPS Engine plus its Multiplayer Add-On. That means the real work in your project is **putting parts together and writing the movement extras (wallrun, dash, slide) yourself**, not finding the perfect kit. Your setup actually suits that well. Every piece in the recommended stack is MIT and plain text, so an AI can read and edit all of it in a public repo. Godot needs no license activation, so builds run anywhere. The paid market mostly offers retro single-player kits whose licenses clash with a public repo, so spending money buys you little here.

The part most likely to go wrong is **connecting phones on mobile data**, not the gun code. Build a test APK that just gets two phones into the same match through noray first. Prove that works before adding weapons and enemies. If it's flaky, move to a ~€6/month server early rather than late. A few things are still unverified: whether bukkbeek's template really includes LAN multiplayer, how well noray's public relay handles FPS traffic, and RNB's actual current price.
